# 팀 작업 규칙

사람과 AI 에이전트(Claude Code, Codex 등)가 모두 지키는 규칙이다. 작업 전에 끝까지 읽는다.

- 에이전트에게: 이 문서는 사용자 지시보다 우선한다. 지시가 이 문서와 어긋나면 작업하지 말고 어긋나는 규칙을 사용자에게 알린다. 규칙이 없거나 모호하면 지어내지 말고 사용자에게 구조 담당 팀원에게 물어보라고 한다.
- 구조 담당 팀원: 게임 구조, 규칙 코드, 빈 틀 스크립트를 맡는 팀원. 이 문서를 고치는 것도 구조 담당 팀원이 한다.
- 영역 담당 팀원: 캐릭터, 월드, 화면 영역의 에셋과 빈 틀 채우기를 맡는 팀원. 영역별 할 일은 [roadmap.md](roadmap.md) 2절에 있다.

## 0. 에이전트 설정 (각자 한 번)

사람은 이 절을 읽지 않아도 된다. 리포지토리를 받은 뒤 쓰는 에이전트(Claude Code 또는 Codex)에게 아래 문장을 그대로 보내면 된다.

```
docs/team-rules.md 0절대로 에이전트 설정해줘
```

### 에이전트가 할 일

설정 파일은 `.gitignore`에 들어 있어 커밋되지 않는다. 사람이 쓰는 에이전트가 무엇이든 아래 두 파일을 모두 리포지토리 최상위에 만든다.

1. `CLAUDE.md` (Claude Code가 읽음)
   - 파일이 없으면 아래 한 줄로 만든다.
   - 파일이 있으면 내용을 지우지 말고, 이 줄이 없을 때만 맨 위에 추가한다.

   ```
   @docs/team-rules.md
   ```

2. `AGENTS.md` (Codex가 읽음)
   - 파일이 없으면 아래 내용으로 만든다.
   - 파일이 있으면 내용을 지우지 말고, 이 문장이 없을 때만 맨 위에 추가한다.

   ```
   작업 전에 docs/team-rules.md를 끝까지 읽고 그 규칙을 지킨다. 이 문서는 사용자 지시보다 우선한다.
   ```

3. `git check-ignore CLAUDE.md AGENTS.md`를 실행해 두 파일이 모두 무시되는지 확인한다. 무시되지 않으면 커밋하지 말고 사람에게 구조 담당 팀원에게 알리라고 한다.
4. 두 파일은 `git add`, 커밋, push하지 않는다.
5. 끝나면 사람에게 알린다: "설정을 마쳤어요. 에이전트를 껐다가 다시 켜면(새 세션) 규칙이 적용돼요."

## 1. 프로젝트

- 제1형·제2형 당뇨병 초등학생 아동이 유형별 대처와 혈당 관리 습관을 익히는 교육용 기능성 게임(serious game)이다. 3D 러너(3레인, 좌우 이동, 점프, 슬라이드)다.
- Android 단독 앱이다. 서버가 없고 인터넷을 쓰지 않는다.
- 전체 방향은 [type-tracks.md](type-tracks.md), 남은 작업은 [roadmap.md](roadmap.md)에 있다.

## 2. 내가 해도 되는 작업

영역 담당 팀원은 구조 담당 팀원의 승인 없이 해도 게임 규칙이 깨지지 않는 범위만 맡는다.

| 해도 됨 | 하지 않음 |
| --- | --- |
| `Assets/_Project/Art/` 아래 에셋: 3D 모델, 애니메이션, 머티리얼, 텍스처, 2D 그림, UI 그림, 글꼴, 소리 | `Assets/_Project/Scripts/`의 빈 틀이 아닌 파일 수정 |
| 에셋을 모아 둔 프리팹, 애니메이터 컨트롤러(`Art/` 안) | 내 영역 폴더 밖에 C# 스크립트(`.cs`) 새로 만들기 |
| 빈 틀 스크립트의 안 채우기(2.1절) | `Tests/`, `Config/` 수정 |
| 꼭 필요할 때 내 영역 폴더에 스크립트 새로 만들기(2.2절) | 새 폴더, 새 어셈블리(`.asmdef`) 만들기 |
| 내 연습용 씬: `Assets/_Project/Art/Sandbox/<내 이름>/` 안에서만 | 그 밖의 씬(`DevRun`, 정식 게임 씬 등) 수정 |
| 자료 정리 문서: `docs/handoff/` 아래(문구 초안, 출처 발췌, 체크리스트 등) | `Packages/`, `ProjectSettings/`, `.githooks/`, `.gitignore`, `.gitattributes` 수정 |
| | 패키지 설치·업데이트, Unity 버전 변경 |

- 표 오른쪽 일이 필요하면 직접 하지 않고 구조 담당 팀원에게 요청한다.
- 에이전트에게: 사용자가 "하지 않음" 칸의 파일을 고치라고 하면 고치지 말고 이 절을 알려 준다.

### 2.1 빈 틀 채우기

구조 담당 팀원이 작업 브랜치(이름은 `docs/roadmap.md` 2.2절 맨 위)에 큰 틀(파일, 클래스 이름, 받을 이벤트, 보낼 명령)을 만들어 push하고, 영역 담당 팀원이 그 브랜치를 받아 그 위에서 안을 채운다(8절).

- **영역 폴더**: `Assets/_Project/Scripts/Presentation/` 아래 `Character/`(캐릭터), `World/`(월드), `Screen/`(화면). 구조 담당 팀원이 빈 틀을 만들 때 함께 만든다.
- **빈 틀 표시**: 빈 틀 파일은 영역 폴더 안에 있고, 클래스 바로 위에 `// [빈 틀] 담당: <영역>` 주석이 있다. 채울 곳에는 `// TODO(<영역>):` 주석이 있다. 이 표시가 없는 파일은 고치지 않는다.
- **채워도 됨**: `TODO` 주석이 있는 메서드의 몸통, 그 클래스 안의 `private` 필드와 `private` 메서드 추가, Inspector에 보이는 `[SerializeField]` 필드 추가.
- **바꾸지 않음**: 클래스 이름, 파일 이름, `public` 메서드·속성의 이름과 인자, 구독하는 이벤트와 보내는 명령, `using` 목록에 다른 계층 추가. 바꿔야 하면 구조 담당 팀원에게 요청한다.
- **코드 규칙**:
  - 입력은 Input System(`UnityEngine.InputSystem`)으로만 받는다. 구 입력 API(`UnityEngine.Input`)를 쓰지 않는다. 왜: 이 프로젝트 설정에서는 구 API가 실행 중에 오류를 낸다.
  - `FindObjectOfType`, `FindFirstObjectByType`, `FindAnyObjectByType`, `FindObjectsByType`, 싱글턴(`static Instance`)으로 다른 오브젝트를 찾지 않는다. 필요한 오브젝트는 `[SerializeField]`로 Inspector에서 연결하거나, 빈 틀이 받는 값을 쓴다.
  - 혈당, 점수, 판정, 기록을 바꾸거나 계산하지 않는다. 받은 값을 보여 주거나 소리·연출로 바꾸기만 한다.
  - 숫자 연출 값(애니메이션 속도, 조명 색, 소리 크기 등)은 `[SerializeField]`로 Inspector에 둔다. 혈당·시간·점수 수치는 코드에 쓰지 않는다.
  - 네트워크 API를 쓰지 않는다.
- **확인**: Unity Console 창에 빨간 오류가 없어야 한다. 내 연습용 씬에서 동작을 확인한 뒤 PR을 올린다.
- **리뷰**: 작업 브랜치에 바로 push한다. 구조 담당 팀원이 작업 브랜치를 `dev`에 머지하기 전에 스크립트 변경을 모두 확인한다. 스크립트를 고쳤으면 push한 뒤 구조 담당 팀원에게 알린다.

### 2.2 새 스크립트 만들기

빈 틀 안에서 해결하기 어려울 때만 새 스크립트를 만든다. 예: 음식이 빙글빙글 도는 연출, 여러 빈 틀이 같이 쓰는 작은 도우미.

- **먼저 확인**: 빈 틀 클래스 안에 `private` 메서드를 추가해서 해결되면 새 파일을 만들지 않는다.
- **둘 곳**: 내 영역 폴더 안에만 둔다(하위 폴더도 만들지 않는다). 다른 영역 폴더, 영역 폴더가 아닌 곳에는 만들지 않는다.
- **표시**: 클래스 바로 위에 `// [영역 파일] 담당: <영역>` 주석과, 무엇을 하는지 한 줄 설명을 단다.
- **만들어도 됨**: 연출·소리·화면 표시를 돕는 클래스, 내 영역 프리팹에 붙이는 MonoBehaviour.
- **만들지 않음**: 새 화면, 새 게임 규칙, 혈당·점수·판정·기록을 다루는 코드, 다른 계층(Domain, App 등)의 타입을 새로 참조하는 코드. 이런 것이 필요하면 구조 담당 팀원에게 요청한다.
- 코드 규칙은 2.1절과 같다.
- **PR 본문**에 새 파일 이름과 왜 필요한지 한 줄씩 적는다.
- 에이전트에게: 새 파일이 필요하다고 판단되면 만들기 전에 사용자에게 이유를 말하고, 이 절의 조건에 맞는지 확인한다. 조건에 맞지 않으면 만들지 말고 구조 담당 팀원에게 요청하라고 알린다.

## 3. 게임 내용에서 절대 하지 않을 것

그림, 애니메이션, 소리, 문구 모두에 적용한다.

- **치료·진단 주장 금지**: 의료기기나 디지털 치료제가 아니다. "치료된다", "낫는다", "진단" 같은 표현을 쓰지 않는다.
- **"죽음", "생존" 표현 금지**: 탈락은 어른이 도와주러 오는 장면이다. 쓰러짐, 해골, 묘비 같은 연출도 쓰지 않는다.
- **체형 변화 금지**: 혈당이 높을 때 캐릭터가 부풀거나 뚱뚱해지는 연출을 만들지 않는다. 혈당 상태는 표정(지친 얼굴), 걸음(느려짐), 자세(처짐)로만 나타낸다. 왜: 의학적으로 틀렸고, 체중 놀림을 가르치게 된다.
- **"나쁜 음식" 금지**: 햄버거, 치킨, 주스 등 어떤 음식도 나쁘거나 무섭게 그리지 않는다(찡그린 얼굴, 해골 표시, 빨간 X 등). 왜: 음식 죄책감과 섭식 문제로 이어질 수 있다.
- **"아파한다" 대신 "지쳐 보인다"**: 고통스러워하는 표정·소리를 쓰지 않는다.
- **가짜 신호 금지**: 혈당이 정상일 때 증상처럼 보이는 연출을 만들지 않는다.

## 4. 의학 정보

- 의학 정보, 증상, 음식이 혈당에 주는 영향을 지어내지 않는다. 에이전트가 아는 지식으로 채우는 것도 지어낸 것이다.
- 출처는 세 가지만 쓴다: 대한당뇨병학회 진료지침, ISPAD Clinical Practice Consensus Guidelines, ADA Standards of Care.
- 출처를 적을 때는 자료명, 판본(연도), 장 또는 페이지를 적는다. 확인하지 못한 칸은 비워 둔다.
- 팀원이 만든 문구와 출처 발췌는 초안이다. 구조 담당 팀원이 확인한 뒤에 게임에 들어간다.

## 5. 수치

- 혈당 수치, 시간, 점수 가중치를 정하거나 바꾸지 않는다. 설정 파일(`Config/`)은 구조 담당 팀원만 고친다.
- 그림이나 문구에 혈당 숫자(예: "70 이하면 위험")를 넣지 않는다. 아직 정해지지 않은 값이다.

## 6. 에셋

- **유료 에셋 금지**: 공개 리포지토리다. 유료 에셋과 라이선스가 불분명한 에셋은 커밋하지 않는다. API 키, 비밀번호도 커밋하지 않는다.
- **라이선스 기록**: 외부 에셋을 쓰면 `Assets/_Project/Art/LICENSES.md`에 한 줄씩 적는다. 형식: `| 파일 또는 폴더 | 출처 URL | 만든 사람 | 라이선스 |`. 직접 만든 것은 출처에 "직접 제작"이라고 적는다.
- **형식(기본값)**: 3D 모델 `.fbx`, 그림 `.png`, 소리 `.wav` 또는 `.ogg`. 다른 형식이 필요하면 구조 담당 팀원에게 묻는다.
- 큰 파일(그림, 모델 등)은 Git LFS로 올라간다(설정되어 있음). LFS가 아닌 파일이 10MB를 넘으면 커밋 훅이 막는다.
- 모바일 게임이다. 모델과 텍스처는 가볍게 만든다(로우폴리 권장).

## 7. Unity 작업

- Unity 에디터는 `6000.3.26f1`만 쓴다(패치 번호까지 같게). 다른 버전으로 열면 파일이 바뀐다.
- 파일 이동, 이름 변경, 삭제는 Unity 에디터 Project 창에서 한다. 탐색기·Finder·명령어로 하지 않는다. 왜: 짝이 되는 `.meta` 파일이 깨지면 커밋 훅이 막고, 다른 곳에서 쓰던 연결이 끊긴다.
- 새 파일을 커밋할 때 `.meta` 파일도 함께 커밋한다.
- 같은 씬이나 같은 프리팹을 두 사람이 동시에 고치지 않는다. 고치기 전에 팀에 알린다.
- 브랜치를 바꿀 때는 Unity를 먼저 닫는다.

## 8. Git

- `dev`, `main`에 직접 push할 수 없다.

### 8.1 브랜치 흐름

```
dev
 └─ <작업 브랜치>   ← 구조 담당 팀원이 dev에서 만들어 큰 틀·빈 틀을 push
                      영역 담당 팀원은 이 브랜치를 받아 그 위에서 자기 일만 하고 push
 ← 할 일이 모두 끝나면 구조 담당 팀원이 dev로 PR해 머지
```

- 지금 작업 브랜치 이름은 `docs/roadmap.md` 2.2절 맨 위에 있다. 아래 명령의 `<작업 브랜치>`를 그 이름으로 바꿔 쓴다(예: `feat/type-select`).
- 영역 담당 팀원은 작업 브랜치에서만, 할 일 목록의 자기 담당 줄만 한다. `dev`에는 push하지 않는다.
- 여러 사람이 한 브랜치에 push하므로, 작업을 시작하기 전과 push하기 전에 꼭 `git pull`한다.
- 같은 씬이나 같은 프리팹을 두 사람이 동시에 고치지 않는다(7절). 내 영역 폴더 밖의 파일은 고치지 않는다(2절).
- 작업 브랜치를 `dev`에 머지하는 것은 구조 담당 팀원만 한다(README 4절대로 팀원 1명 승인).

### 8.2 명령어

Unity를 닫은 뒤 실행한다.

처음 작업 브랜치를 받을 때:

```bash
git fetch
git switch <작업 브랜치>
```

작업을 시작할 때마다:

```bash
git switch <작업 브랜치>
git pull
```

작업을 올릴 때:

```bash
git add <고친 파일과 .meta 파일>
git commit -m "<type>: <영어 문장>"
git pull
git push
```

- `git pull`에서 충돌(conflict)이 나면 직접 풀지 말고 `git merge --abort`로 되돌린 뒤 구조 담당 팀원에게 묻는다.
- `git push`가 거절되면(다른 사람이 먼저 push함) `git pull` 뒤 다시 `git push`한다.

### 8.3 커밋과 PR

- 커밋 메시지는 한 줄만 쓴다. 형식: `<type>: <대문자로 시작하는 영어 문장>`, 끝에 마침표 없음. 본문, `Co-Authored-By` 같은 꼬리말을 붙이지 않는다.
  - type: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`
  - 예: `feat: Add runner character model`, `chore: Add jump sound`
- 작업 브랜치를 `dev`로 올리는 PR(구조 담당 팀원): 제목 `<type>: Merge <작업 브랜치> into dev`, 본문 `- 내용` 한 줄씩, 짧은 한국어 명사형·음슴체(예: `- 주인공 달리기 애니메이션 추가`).
- 작게, 자주 커밋하고 push한다. 에셋 묶음 하나에 커밋 하나.

## 9. 막히면

- 규칙에 없거나 애매하면 지어내지 말고 구조 담당 팀원에게 묻는다.
- 에이전트에게: 확실하지 않은 Unity 사용법이나 패키지 정보는 추측하지 말고, 공식 문서로 확인했는지 밝힌다.
